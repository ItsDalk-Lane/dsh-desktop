# Agent Note: Vision-enhancement model setting is a standing entry

Status: implemented

[English](2026-08-29-vision-model-standing-setting.md) | 中文

## Problem

兼容视觉的提供方与模型只能在验证弹窗里配置，而弹窗只在开启流程中可达：设置行在开关关闭时打开它，输入区快捷按钮只在激活失败时打开它。能力处于开启状态——也就是它的常态——时，更换视觉模型必须先关闭再重新开启。Host 的 `vision.enable` 操作本身就支持在已开启状态下原子重配（先禁用、用一张真实图片重新验证、再持久化新选择），缺口纯粹是入口可达性，不是能力缺口。

## Decision

两个入口面各保留一个与开关无关的常态设置入口。设置行在开关旁常驻「设置」按钮，无论开关状态如何都打开验证弹窗。输入区快捷按钮的悬浮卡携带「更换视觉模型」（开启态）／「设置视觉模型」（关闭态）动作，打开同一个弹窗。弹窗新增镜像 Host 状态的 `reconfigure` 标志：已开启时文案为「视觉能力增强设置／验证并应用／识别成功，视觉模型已更新」，提交仍走同一条原子 `vision.enable` 路径，因此验证通过后新提供方或模型立即生效，无需关闭再重开。开关在两个入口面保持既有语义；Host 侧"仅允许关闭"的设置守卫不变：开启与改模型仍然要求真实图片验证。

## Alternatives considered

**通过普通设置命名空间直接 patch 模型。** 不予采纳，因为 Host API proxy 刻意只对 `vision-enhancement` 命名空间放行"仅关闭"的写入；提供方与模型变更必须继续通过真实图片验证，避免把一个不可用的视觉模型持久化为已开启。

**开启态下让开关打开弹窗而不是执行关闭。** 不予采纳，因为开关会因此藏起"关闭"这一最高频操作，用一个新的缺失入口换取另一个。

**取消重新验证、即时应用模型修改。** 不予采纳，因为验证探针是唯一能端到端确认所配置的凭证、服务地址与模型 ID 真的能一起识别图片的检查；跳过它会让拼写错误在请求时才击垮兼容路线。

## Verification

`packages/client/ui-desktop-customization/tests/vision.client.spec.tsx` 钉住两个入口面的常态入口：设置行的「设置」按钮在已开启状态打开重配弹窗，「验证并应用」在没有任何关闭调用的情况下提交同一探针；输入区悬浮卡在两种开关状态下都暴露该动作，开启态动作打开重配弹窗。首次开启流程保持原有「开启」文案。

## Consequences

视觉模型在任一入口面随时可改，且变更与首次配置受同一验证保护。设置行多出一个控件；输入区悬浮卡多出一个可键盘聚焦的按钮，但悬浮卡本身只能悬停唤出，键盘用户经由设置行完成配置。
